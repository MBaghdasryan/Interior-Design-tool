# ADR-004: Persisted jobs with in-process pool

**Статус:** принято · 2026-10-21

## Контекст и решение
Шаги и прогресс хранятся в БД и стримятся по SSE; FORMA_JOBS_SYNC=1 делает тесты детерминированными.

## Последствия
Для горизонтального масштабирования заменить драйвер на Redis/RQ/Celery/Temporal без изменения кода задач.

## Обновление 2026-10-22 (P1-1): Redis + RQ

**Статус:** принято. Драйвер очереди выбирается автоматически.

| Режим | Когда | Как |
|---|---|---|
| Redis + RQ | задан `REDIS_URL` (compose) | задачи выполняет отдельный сервис `worker` (`python -m app.worker`) |
| Thread pool | локальная разработка без Redis | при старте API незавершённые задачи перезапускаются |
| Inline | `FORMA_JOBS_SYNC=1` | тесты и CLI |

**Почему RQ, а не Celery или Temporal.** Задачи короткие и линейные, состояние уже хранится в Postgres. RQ — минимальная зависимость: одна очередь, повторы с паузой (scheduler), реестр упавших задач, warm shutdown по SIGTERM, тестируется с fakeredis.

**Гарантии:**
- Повторы: 3 попытки, паузы 15 с и 60 с.
- После исчерпания попыток: `counters.dead_letter=true` в БД, задача остаётся в FailedJobRegistry на 7 дней.
- Идемпотентность: ключ `idempotency_key` проверяется до постановки в очередь.
- Осиротевшие задачи: `queued`/`running` без живого worker'а (по heartbeat RQ) переставляются в очередь при старте worker'а и каждую минуту в maintenance-цикле. Проверено живым `SIGKILL` worker'а посреди задачи: попытка 2 завершилась успешно.
- Fork-безопасность БД: `os.register_at_fork` → `engine.dispose(close=False)`.
- SSE: каждое событие несёт `id` (хэш состояния) и `retry: 3000`. После переподключения браузер присылает `Last-Event-ID`, и неизменённое состояние повторно не отправляется. Polling включается только после трёх ошибок подряд.

**Риск:** повторный запуск задачи `pipeline`, упавшей посередине, создаёт варианты заново — старые незавершённые варианты остаются в проекте. Задача идемпотентна по ключу запуска, но не по промежуточным артефактам.
