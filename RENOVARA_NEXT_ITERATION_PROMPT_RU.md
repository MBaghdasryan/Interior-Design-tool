# MASTER PROMPT — Renovara: закрытие всех нереализованных пунктов

Этот промпт для агента (Claude Code / Codex), который продолжает работу в репозитории
`https://github.com/MBaghdasryan/Interior-Design-tool`.

Цель — пройти по каждому пункту ниже. По каждому пункту есть два исхода:
- **реализовать и доказать** тестом, артефактом или E2E;
- если мешает внешняя зависимость, **довести до границы интеграции** (адаптер, конфиг, contract-тест, UI с честным статусом) и пометить `BLOCKED_BY_EXTERNAL_DEPENDENCY` с указанием, что именно нужно от владельца.

| Действие | Команда |

## 1. Обязательные правила

1. **Не ломать то, что работает.** После каждого среза прогоняются все проверки из §0. Регрессия чинится до перехода к следующему пункту.
2. **Каждое изменение схемы БД — отдельная Alembic-миграция** с рабочим `downgrade()`. Миграция проверяется upgrade → downgrade → upgrade на Postgres.
3. **Все новые UI-строки — только через i18n** (`hy/ru/en`, все три обязательны). Коды ошибок API добавляются в `app/errors.py` и в `errors.*` словаря. Если меняются разделы `works/notice/rules/enum/unit/estimate.line_*`, перегенерируй `i18n_shared.json`.
4. **Каждый эндпоинт:**
   - проходит через `project_access()` или эквивалентную проверку прав и тенанта;
   - пишет `AuditEvent` для изменяющих операций;
   - для денежных и заказных операций принимает ключ идемпотентности.
5. **Секреты.** Никогда не печатать и не логировать ключи и токены. `.env` не коммитить. Новые переменные — в `.env.example` с безопасным значением по умолчанию.
6. **Честность:**
   - не выдумывать SKU, цены и наличие;
   - DEMO-данные явно помечены;
   - не имитировать успешную оплату без платёжного провайдера;
   - не писать «платформа готова».
7. **Внешние сайты:** не обходить robots, CAPTCHA, логин и paywall. `EXTERNAL_FETCH_LIVE=false` по умолчанию. Новый источник включается только после policy-аудита.
8. **Работать вертикальными срезами** (модель → миграция → API → UI → тесты → документация). После каждого среза — отдельный git-коммит с понятным сообщением.
9. **Статус каждой функции:** `VERIFIED`, `IMPLEMENTED_NOT_LIVE_VERIFIED`, `PARTIAL`, `STUB/DEMO`, `NOT IMPLEMENTED`, `BLOCKED_BY_EXTERNAL_DEPENDENCY`.

## 2. Порядок выполнения

Сначала P0, затем P1, затем P2. Внутри приоритета — по номерам.

### P0-1. Регистрация, онбординг, восстановление пароля

- **Эндпоинты:**
  - `POST /auth/register` — создаёт пользователя и организацию (бюро или поставщик) по выбранному типу;
  - `POST /auth/verify-email`;
  - `POST /auth/password/forgot`;
  - `POST /auth/password/reset`.
- **Токены** одноразовые, с TTL, в БД хранится только их хэш.
- **Email** — абстракция `EmailSender`:
  - dev: `console`/`file` sender, письма пишутся в `data/mail/`;
  - prod: SMTP (`SMTP_*` в env).
- **UI:** экраны регистрации, подтверждения, сброса пароля; онбординг из 3 шагов (организация → роль → первый проект).
- **Защита от перебора:** ограничение попыток входа и сброса (см. P0-3).
- **Приёмка:** тесты регистрации, повторного email, истёкшего токена; E2E: регистрация → подтверждение → вход → создание проекта.

### P0-2. Безопасность для публичного запуска

Пункты S1–S3 и S13 из `SECURITY_REPORT.md`.

- **Токен** перенести из `localStorage` в cookie `HttpOnly; Secure; SameSite=Lax`.
- **Отзыв сессий** — серверная таблица `Session` (id, user, device, ip, created, last_seen, revoked).
- **CSRF:** double-submit token для изменяющих запросов.
- **SSE** — авторизация по cookie вместо `?token=`.
- **Rate limit:**
  - на `/auth/*` и тяжёлые эндпоинты (генерация, discovery, альбом);
  - Redis-backend, если P1-1 уже сделан, иначе in-memory с интерфейсом под Redis.
- **Демо-режим:** при `ENV=production` демо-аккаунты и `/auth/demo-accounts` отключены; при старте проверка, что `SECRET_KEY` не шаблонный, иначе отказ запускаться.
- **Приёмка:**
  - тесты: CSRF отклоняет запрос без токена, rate limit возвращает 429, отозванная сессия не работает, prod-режим без демо;
  - E2E 22/22 и маршруты 20/20 остаются зелёными.

### P0-3. Второй рабочий источник внешнего каталога

- **Policy- и технический аудит** VLV или Nor Tun (robots, sitemap, JSON-LD, наличие фида/API). Результат — в `EXTERNAL_CATALOG_REPORT.md`.
- **Если разрешено:** коннектор через общий контракт, parser fixtures, contract-тесты, `live_enabled=true` только для него.
- **Если запрещено или нет фида:** коннектор фида (CSV/XLSX/XML/JSON) с маппингом и предпросмотром, контрактный тест на фикстуре. Статус `BLOCKED_BY_EXTERNAL_DEPENDENCY: нужен фид от магазина`.
- **Приёмка:** E2E «включить внешний каталог → shortlist из двух источников → вариант → смета со ссылками на оба источника» (на фикстурах без сети, плюс один live smoke при наличии разрешения).

### P0-4. Пилот N99

Блокирован до получения материалов от владельца (список — в `N99_VALIDATION_REPORT.md`).
- **Пока материалов нет:** не создавать фиктивные данные. Довести UI пилота: загрузка по манифесту и экспорт отчёта пилота в PDF/JSON.
- **Когда материалы есть:**
  - полный проход по 10 этапам чек-листа;
  - альбом hy, sign-off специалиста;
  - обновить `N99_VALIDATION_REPORT.md` фактическими результатами, перечнем допущений и рисков;
  - статус «validated» только если все 20 пунктов зелёные.

### P1-1. Очередь задач и отдельный worker

- Redis + RQ (или Arq) вместо `ThreadPoolExecutor`; отдельный сервис `worker` в compose.
- **Поведение задач:**
  - идемпотентность сохраняется;
  - повторы с backoff;
  - dead-letter;
  - graceful shutdown;
  - задача не теряется при рестарте API.
- **Локальная разработка:** без Redis сохранить режим `FORMA_JOBS_SYNC`/inline, чтобы Redis не был обязателен.
- **SSE:** поддержка `Last-Event-ID` и возобновления потока; polling только как fallback.
- **Приёмка:** тесты повтора, идемпотентности и восстановления после рестарта worker; тест возобновления SSE.

### P1-2. Хранилище, бэкапы, наблюдаемость

- **Хранилище:**
  - интерфейс `Storage` с реализациями `LocalStorage` и `S3Storage` (MinIO в compose-профиле `prod`);
  - загрузка через presigned URL, шифрование на стороне хранилища.
- **Бэкапы:** скрипт бэкапа и восстановления Postgres и хранилища, runbook `docs/RUNBOOK.md`, проверка восстановления в отдельной БД.
- **Логи:** структурированные (JSON) с trace id.
- **Наблюдаемость:**
  - OpenTelemetry-трейсы (FastAPI, SQLAlchemy, httpx);
  - Sentry-совместимый DSN из env (выключен по умолчанию);
  - эндпоинты `/health`, `/ready`, `/live`.
- **Продакшен:** compose-профиль `prod` с reverse proxy (Caddy/Traefik) и TLS, без демо-сида. Политика хранения и удаления файлов.

### P1-5. AI: провайдеры, квоты, оценка качества

- **Внешние зависимости:** OpenAI (кредиты), платный Gemini (Pro и модели изображений), ключ Anthropic. Без них — `BLOCKED`, но с работающими адаптерами и contract-тестами.
- **Квоты и стоимость:**
  - квоты и лимиты стоимости на организацию (дневной и месячный бюджет в USD);
  - отказ с кодом `ai.quota_exceeded`;
  - отображение расхода в кабинете бюро.
- **Набор для оценки** (`apps/api/evals/`):
  - ≥30 планов разного качества с эталонной геометрией;
  - ≥30 AI-команд с ожидаемыми операциями;
  - проверки «нет выдуманных SKU», соблюдение бюджета, стабильность повторной генерации;
  - команда `python -m evals.run`, отчёт `EVAL_REPORT.md` с метриками по провайдерам.
- **Фото-рендер** (после биллинга):
  - генерация по SKU-манифесту сцены с контролем камеры и геометрии (depth/segmentation);
  - маска зоны и перегенерация отдельной области;
  - high-res экспорт;
  - product-grounding score на каждый объект;
  - объект без точного соответствия помечается «визуальный аналог»;
  - рендеры попадают в альбом (ДН4) и в Client Viewer.
- **Blender/Cycles worker** — отдельный опциональный сервис с тем же интерфейсом `RenderProvider`.
